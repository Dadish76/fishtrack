## 1. Общие сведения

- Идентификатор: `incident-20261126-004054-e81158`.
- Дата: 26.11.2026 (локальное время, UTC+3 согласно снимкам; журналы контейнеров — UTC).
- Тип: контролируемый учебный отказ PostgreSQL, лабораторная работа №8, пункт 13.
- Среда: локальный Docker Desktop, Compose-проект `fishtrack-lab8-20261125201915`.
- Версия приложения: `sha-5d682aa68fd16bf4274c005e769d5ae81db228e2`.
- Затронутая зависимость: PostgreSQL; затронутые экземпляры приложения: app1, app2.
- Итог: работоспособность восстановлена; исторические журналы и дополнительная приемка подтверждены.

## 2. Обнаружение и влияние

До отказа оба экземпляра возвращали HTTP 200 на `/health` и `/live`; `up` и `fishtrack_app_healthy` равнялись 1 для каждого экземпляра. Все пять правил Prometheus были неактивны и вычислялись без ошибок.

После контролируемой остановки БД оба экземпляра продолжили отдавать метрики (`up=1`), но потеряли готовность (`fishtrack_app_healthy=0`). В журналах каждого экземпляра зафиксированы три HTTP 503 на `/health` до запуска БД. Правило `FishTrackNotReady` перешло в Pending, затем в Firing уже на этапе восстановления. `FishTrackInstanceDown` оставалось неактивным.

Операции, требующие подключения к БД, оказались под угрозой недоступности. Фактическая доля ошибок пользовательских операций, объем потерянных запросов и состояние `/live` непосредственно во время отказа отдельно не измерялись. Потеря данных не установлена; полная проверка целостности всех данных не проводилась.

## 4. Подтверждение первопричины

Первопричина учебного инцидента — намеренная остановка единственной PostgreSQL, от которой зависят оба экземпляра приложения. Доказательства:

Четыре исходных HTTP-проверки до отказа сопоставлены с журналами по `request_id`. Прямые HTTP-пробы во время отказа не сохранены; корреляция их заголовков с журналами не подтверждена.

## 6. Недостатки и последующие действия

Правило `FishTrackNotReady` с `for: 30s` зависит от периодической проверки готовности, сбора метрик и вычисления правила. В данном эксперименте Firing наблюдалось примерно через 65 с после остановки БД, уже после начала восстановления. Показатель `up` сам по себе не позволяет обнаружить отказ зависимости, если приложение продолжает отдавать метрики.

Первый сценарий завершил сбор доказательств досрочно: `incident.json` имеет статус `incomplete`. Точная причина прерывания не установлена. Восстановление выполнено защитным блоком `finally`; недостающие исторические журналы собраны отдельным сценарием без нового отказа. Исходный JSON сохранен неизменным, дополнение имеет статус `historical_logs_and_recovery_verified`.

Предлагаемые действия для этапа 14 (еще не реализованы): ускорить обнаружение недоступности БД, добавить проверяемое правило раннего обнаружения и регрессионный тест правил; повторить контролируемый эксперимент и сравнить интервалы обнаружения по единой методике. Не ослаблять существующие проверки и не выдавать ожидаемое ускорение за измеренный результат.

# FishTrack — улучшение процесса обнаружения инцидентов

## 1. Основание и область применения

Лабораторная работа №8, пункт 14. По результатам контролируемого отказа PostgreSQL (см. [Postmortem](incident-postmortem.md)) правило `FishTrackNotReady` впервые наблюдалось в состоянии Firing через 64,7 с после остановки БД, уже после начала восстановления. Цель изменения — сократить задержку обнаружения общего отказа готовности приложения.

Эксперимент проведен 26 ноября 2026 года в локальной среде Docker Desktop, проект `fishtrack-lab8-20261125201915`, версия приложения `sha-5d682aa68fd16bf4274c005e769d5ae81db228e2`. Проверка staging на собственной ВМ остается отдельной незавершенной задачей этапа 11.

## 2. Изменение конфигурации

Добавлено правило `FishTrackBothInstancesNotReady` в `monitoring/prometheus/rules/fishtrack-fast-alerts.yml`. Существующие пять правил сохранены.

| Параметр | FishTrackNotReady | FishTrackBothInstancesNotReady |
|---|---|---|
| Условие | Отдельный экземпляр не готов, метрики доступны | Оба экземпляра не готовы, метрики обоих доступны |
| Интервал вычисления | 10 с | 5 с |
| Выдержка `for` | 30 с | 5 с |
| Уровень | critical | critical |

Новое правило выявляет общий отказ готовности, а не непосредственно отказ PostgreSQL. Причину необходимо устанавливать с помощью журналов, метрик и эксплуатационной инструкции. При потере доступности одного из targets сохраняет значение правило `FishTrackInstanceDown`.

## 3. Автоматические регрессионные проверки

Добавлены `monitoring/prometheus/tests/fishtrack-fast-alerts.test.yml` и `.github/workflows/monitoring-ci.yml` для проверки конфигурации, синтаксиса правил и их поведения через `promtool test rules`. Предусмотрены сценарии нормальной работы, отказа одного и двух экземпляров, восстановления, краткого нарушения условия и отсутствия необходимых метрик.

По сообщению исполнителя локальные проверки пройдены; отдельный вывод promtool не включен в предоставленный фрагмент журнала. Результат GitHub Actions Monitoring CI необходимо подтвердить после push. Для обязательного запрета слияния при ошибке нужна настройка защиты ветки с соответствующей обязательной проверкой.

## 6. Эксплуатационные ограничения и дальнейшие действия

Короткая выдержка позволяет быстрее обнаружить общий отказ, но увеличивает чувствительность к кратковременным сбоям. Два вычисления правила не обязательно соответствуют двум независимым сборам метрик, так как scrape interval составляет 10 с. Задержка зависит также от healthcheck и сетевого взаимодействия. Один сравнительный эксперимент не устанавливает гарантированное время обнаружения для всех будущих отказов. Правило не обеспечивает автоматическую доставку уведомлений оператору без дополнительной системы оповещений.

При срабатывании использовать [Runbook](observability-runbook.md): проверить доступность метрик, готовность экземпляров, PostgreSQL, журналы и восстановление. Сохранить первичные доказательства; не менять правила только для подавления оповещения.

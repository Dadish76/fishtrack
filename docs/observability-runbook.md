# FishTrack — инструкция диагностики и восстановления (Runbook)

Лабораторная работа №8 · Этап 9

## 1. Назначение и область применения

Инструкция предназначена для диагностики отказов FishTrack с помощью Prometheus, Grafana, структурированных журналов и Docker. Цель — установить причину, восстановить сервис с минимальным вмешательством и проверить результат.

Система: Nginx → два экземпляра FastAPI (app1, app2) → PostgreSQL. Prometheus собирает метрики приложения, Node Exporter и cAdvisor; Grafana визуализирует их. Правила обнаружения проблем вычисляются Prometheus. Доставка внешних уведомлений через Alertmanager в текущую конфигурацию не входит.

Команды ниже проверяются в контексте локальной лабораторной среды Windows PowerShell и Docker Desktop. На app-server необходимо отдельно подтвердить адреса, имена контейнеров, Docker context, сетевую конфигурацию и порядок развертывания. Локальные команды изменения состояния нельзя выполнять на staging или production без адаптации и разрешения.

### Точки доступа локальной среды

| Ресурс | Адрес |
|---|---|
| FishTrack | http://127.0.0.1:18080 |
| Проверка готовности | http://127.0.0.1:18080/health |
| Проверка версии | http://127.0.0.1:18080/version |
| Prometheus Targets | http://127.0.0.1:9090/targets |
| Prometheus Alerts | http://127.0.0.1:9090/alerts |
| Grafana Dashboard | http://127.0.0.1:3000/d/fishtrack-observability/fishtrack-observability |

Маршрут `/metrics` через Nginx должен возвращать HTTP 404. Prometheus получает метрики непосредственно от app1 и app2 во внутренней сети. Пароли и токены в инструкцию, скриншоты и отчеты не включаются.

## 2. Первичная диагностика

Зафиксировать время (с часовым поясом), симптомы, затронутую функцию, текущую версию приложения и недавно выполненные изменения. Не перезапускать все контейнеры до сбора сведений.

```powershell
# Проверяем локальный контекст и состояние контейнеров.
docker context show
docker version
$project = "fishtrack-lab8-20261125201915"
$db = "$project-db-1"
$app1 = "$project-app1-1"
$app2 = "$project-app2-1"
$nginx = "$project-nginx-1"
docker ps -a --filter "label=com.docker.compose.project=$project"
docker ps -a --filter "label=com.docker.compose.project=fishtrack-lab8-monitoring"

# Проверяем ответы приложения через Nginx.
curl.exe -i --max-time 10 http://127.0.0.1:18080/health
curl.exe -i --max-time 10 http://127.0.0.1:18080/version
curl.exe -i --max-time 10 http://127.0.0.1:18080/metrics
```

Нормальное состояние: app1, app2 и PostgreSQL работают и проходят проверки готовности, Nginx работает; `/health` и `/version` возвращают 200, внешний `/metrics` — 404. Служебные одноразовые контейнеры миграций и инициализации могут быть завершены с кодом 0.

Открыть Prometheus Targets и Alerts, затем Dashboard FishTrack Observability (интервал 15–30 минут вокруг проблемы). Проверить пять целей сбора, готовность обоих экземпляров, нагрузку, 4xx/5xx, p95, CPU, RAM, диски и ресурсы контейнеров. При необходимости выбрать правильный Compose-проект. Отсутствие данных не считать нулем или признаком нормальной работы.

## 3. Правила и метрики

| Правило | Условие | Задержка `for` | Первичная диагностика |
|---|---|---|---|
| FishTrackInstanceDown | `up{job="fishtrack"} == 0` | 30 с | Проверить контейнер, сеть, порт и ошибку scrape |
| FishTrackNotReady | `fishtrack_app_healthy == 0` при `up == 1` | 30 с | Проверить PostgreSQL, соединения и журналы приложения |
| FishTrackHighErrorRate | Доля 5xx > 5%, нагрузка ≥ 0,1 запроса/с; окно 2 мин, без служебных маршрутов | 1 мин | Проверить ошибки, маршруты, зависимость от БД и недавний релиз |
| HostHighCPU | CPU > 80%, окно 2 мин | 2 мин | Найти контейнер или процесс с высокой нагрузкой |
| HostHighMemory | Использование RAM > 85% | 2 мин | Проверить память контейнеров, OOM и лимиты |

`inactive` — условие не выполняется; `pending` — выполняется, но еще не выдержана задержка; `firing` — правило сработало. `health: ok` означает успешное вычисление правила, а не отсутствие отказа.

Основные запросы PromQL для диагностики:

```promql
up{job="fishtrack"}
fishtrack_app_healthy{job="fishtrack"}
sum by (instance, status) (rate(fishtrack_http_requests_total{job="fishtrack"}[5m]))
sum by (instance, path, status) (rate(fishtrack_http_errors_total{job="fishtrack",status=~"5.."}[5m]))
1000 * histogram_quantile(0.95, sum by (le) (rate(fishtrack_http_request_duration_seconds_bucket{job="fishtrack",path!~"/health|/live|/metrics"}[5m])))
fishtrack_trips_created_total{job="fishtrack"}
```

Вставлять запросы по одному в Prometheus Query. `up=1` означает успешный сбор метрик, но не гарантирует готовность приложения или доступность через Nginx. `fishtrack_app_healthy` обновляется при проверке `/health`; если сбор метрик прекратился, значение нельзя считать подтверждением текущей готовности. Счетчик рейсов является накопительным и сбрасывается при перезапуске процесса; отсутствие новых рейсов само по себе не означает отказ. Node Exporter в Docker Desktop измеряет ресурсы Linux-среды, а не всей Windows-системы.

## 4. Анализ журналов

Сопоставить время сбоя с метриками и структурированными журналами. Для конкретного HTTP-запроса использовать идентификатор из заголовка `x-request-id`. Он помогает найти запись на нужном экземпляре и в журнале Nginx.

```powershell
# Просматриваем ограниченный интервал журналов.
docker logs --since 15m --tail 100 $app1
docker logs --since 15m --tail 100 $app2
docker logs --since 15m --tail 100 $nginx
docker logs --since 15m --tail 100 $db

# Поиск запроса в структурированных журналах.
$requestId = Read-Host "Введите идентификатор запроса"
foreach ($container in @($app1, $app2, $nginx)) {
    Write-Host "=== $container ==="
    docker logs --since 15m $container 2>&1 | Select-String -SimpleMatch $requestId
}
```

Изучить время, уровень, тип события, шаблон маршрута, результат и идентификатор запроса. Подтверждать причину сочетанием журналов и метрик, а не одним HTTP-кодом. Не публиковать необработанные журналы, значения переменных окружения, строки подключения, cookies, заголовки авторизации и другие секреты. При обнаружении утечки ограничить доступ, сообщить ответственному и организовать замену скомпрометированных секретов.

## 5. Типовые неисправности и восстановление

| Симптом | Диагностика | Восстановление |
|---|---|---|
| Оба экземпляра не готовы, но `up=1` | PostgreSQL, ее журналы, `pg_isready`, ошибки соединения | Восстановить PostgreSQL или исправить подтвержденную причину подключения |
| Один экземпляр имеет `up=0` | `docker ps -a`, журналы, состояние healthcheck, Targets | Запустить остановленный экземпляр; при повторном отказе устранить причину или откатить релиз |
| `/health` через Nginx недоступен, но оба экземпляра готовы | Проверить Nginx, его порт, сеть и конфигурацию | Исправить конфигурацию; запустить Nginx, если он остановлен |
| Рост 5xx или p95 | Сопоставить ошибки, нагрузку, ресурсы, журналы и версию | Устранить причину; при дефектном релизе использовать утвержденную процедуру rollback |
| Высокий CPU или RAM | Grafana, `docker stats`, OOM, ограничения ресурсов | Устранить перегрузку или утечку; менять лимиты только обоснованно |
| Заполнение диска | Метрики файловых систем, `docker system df`, свободное место | Освободить подтвержденные ненужные данные безопасным способом или расширить диск |
| Метрики не поступают | Prometheus Targets, журналы экспортера, сеть, конфигурация | Восстановить конкретный компонент мониторинга; проверить сбор снова |
| Docker Engine недоступен | `docker version`, Docker Desktop, локальный context | Запустить Docker Desktop, затем проверить и при необходимости запустить существующие контейнеры |

Дополнительные команды диагностики:

```powershell
# Состояние БД, Nginx и ресурсов.
docker exec $db pg_isready -h 127.0.0.1 -U fishtrack_lab8 -d fishtrack_lab8
docker exec $nginx nginx -t
docker stats --no-stream
docker system df
docker inspect --format '{{.State.Status}} OOMKilled={{.State.OOMKilled}}' $app1 $app2 $db
```

`pg_isready` проверяет прием соединений PostgreSQL, но не подтверждает работоспособность SQL-запросов приложения. При остановленной БД `docker exec` не сработает — проверить состояние контейнера и журналы.

Если подтверждено, что локальная БД остановлена, и необходимо ее запустить:

```powershell
# Выполнять только в известном локальном тестовом окружении.
& {
    $ErrorActionPreference = "Stop"
    if ((docker context show) -ne "desktop-linux") { throw "Неверный Docker context" }
    $project = "fishtrack-lab8-20261125201915"
    $db = "$project-db-1"
    $containers = @(docker --context desktop-linux ps -a --filter "label=com.docker.compose.project=$project" --filter "label=com.docker.compose.service=db" --format "{{.Names}}")
    if ($LASTEXITCODE -ne 0 -or $containers -notcontains $db) { throw "Тестовая БД не найдена" }
    docker --context desktop-linux start $db
    if ($LASTEXITCODE -ne 0) { throw "Ошибка запуска PostgreSQL" }
}
```

При необходимости запустить существующие app1 и app2 после готовности БД, затем Nginx. Не пересоздавать БД и не удалять volumes. При дефектном релизе сохранить доказательства, определить предыдущую стабильную версию и использовать действующую процедуру отката проекта; проверить совместимость миграций и состояние данных. Не применять `docker compose down -v`, `docker volume prune`, `docker system prune` или сброс Docker Desktop в качестве стандартного восстановления.

## 6. Проверка после восстановления

1. Убедиться в готовности контейнеров и доступности сервиса: `/health` — 200, `/version` — ожидаемый релиз, внешний `/metrics` — 404.
2. Проверить Targets: пять целей UP. Для app1 и app2 обе метрики `up` и `fishtrack_app_healthy` равны 1.
3. Проверить, что относящиеся к инциденту правила вернулись в `inactive`, вычисляются с `health: ok`; проверить отсутствие новых неожиданных оповещений.
4. Запустить функциональный smoke-тест в тестовом окружении (он создает и удаляет тестовую запись):

```powershell
python scripts/smoke_test.py --base-url http://127.0.0.1:18080 --expected-tag fishtrack-lab8-20261125201915 --boat-payload-file scripts/smoke_boat.json
```

Ожидается `PASS: FishTrack create → read → compare → delete → 404`. Для другого релиза подставить его фактический тег. Проверить, что уровень ошибок и задержки вернулись к обычным значениям. Если восстановление не подтверждено, продолжить диагностику или передать проблему ответственному.

Во время контрольной проверки `up=1`, `fishtrack_app_healthy=0` для обоих экземпляров; после восстановления обе метрики равны 1. Между наблюдаемыми pending и firing прошло 30 секунд, между первым опросом после остановки и firing — 65 секунд, между первым опросом после запуска и inactive — 25 секунд. Это интервалы наблюдения, не точное время внутренних переходов.

## 8. Фиксация инцидента

В отчете или задаче указать время и окружение, симптом, затронутый компонент, версию, правило, доказательства из журналов и метрик, выполненные действия, результат проверки, остаточные риски и предложения по предотвращению повторения. Сохранить необходимые скриншоты без секретов. При изменении процедуры диагностики обновить Runbook через Git.

## 9. Ускоренное обнаружение общей потери готовности

Правило FishTrackBothInstancesNotReady обнаруживает
одновременную потерю готовности app1 и app2 при сохранении
доступности их метрик.

Параметры правила:

- Интервал вычисления: 5 секунд.
- Период ожидания: 5 секунд.
- Уровень критичности: critical.

Порядок действий при срабатывании:

1. Проверить метрики up и fishtrack_app_healthy.
2. Проверить состояние PostgreSQL.
3. Проверить журналы базы данных и приложения.
4. Определить и устранить первопричину.
5. Подтвердить восстановление готовности обоих экземпляров.
6. Проверить снятие оповещений.
7. Выполнить Smoke Test.

Новое правило дополняет существующие правила,
но не заменяет диагностику первопричины.

В контрольном эксперименте время обнаружения составило
30,129 секунды вместо 65,260 секунды для обоих экземпляров
по старому правилу.

Сокращение задержки составило 53,83%.

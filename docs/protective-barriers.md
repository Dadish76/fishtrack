# FishTrack — автоматические и организационные барьеры

Лабораторная работа №8, пункт 15.

## 1. Назначение

Защитные барьеры снижают вероятность выпуска дефектного изменения, помогают обнаруживать сбои в работающей системе и обеспечивают контролируемое восстановление. Автоматические барьеры выполняются программными средствами; организационные определяют порядок действий и принятия решений. Не каждый инструмент наблюдаемости блокирует выпуск: часть инструментов предназначена для обнаружения и диагностики проблем после развертывания.

## 2. Автоматические барьеры

| Механизм | Назначение | Стадия |
|---|---|---|
| Black, Ruff | Проверка форматирования и качества кода | Локальная проверка, CI |
| Bandit | Статический анализ безопасности Python | Локальная проверка, CI |
| Pytest, Coverage | Проверка функциональности, порог покрытия 40% | Локальная проверка, CI |
| pip-audit, Gitleaks | Поиск известных уязвимостей зависимостей и секретов | CI |
| Alembic | Проверка применимости миграций | CI, развертывание |
| Backup and Restore | Проверка сценария резервного копирования и восстановления | CI |
| Container Check | Проверка конфигурации, запуска, балансировки, отказоустойчивости и безопасности контейнеров | Локальная проверка, CI |
| Trivy | Анализ уязвимостей образа | CI перед публикацией |
| Monitoring CI, promtool | Проверка конфигурации, правил и регрессионных сценариев мониторинга | CI |
| SHA-тег Docker-образа | Прослеживаемость версии до коммита | Сборка, публикация и выпуск |
| Healthcheck, /health, /live | Контроль готовности и жизнеспособности приложения | Развертывание, эксплуатация |
| Smoke Test | Проверка версии и основных операций с данными | Приемка релиза, восстановление |
| Структурированные журналы, request_id | Сопоставление запросов и результатов, диагностика без записи секретов в предусмотренных путях логирования | Эксплуатация |
| Prometheus, Grafana, Node Exporter, cAdvisor | Наблюдение за доступностью, нагрузкой, задержками, ошибками, ресурсами и предметной метрикой | Эксплуатация |
| Правила Prometheus | Обнаружение недоступности и потери готовности, повышенной доли 5xx, высокой загрузки CPU и RAM | Эксплуатация |
| Сохранение предыдущего тега и сценарий отката | Возможность контролируемого возврата предыдущей версии; откат не требуется при каждом отказе | Восстановление |

Наличие проверки в CI означает, что ее ошибка может остановить зависимые задания workflow. Принудительный запрет слияния при неуспешной проверке требует отдельных настроек защиты ветки; их обязательность в рамках данной работы не подтверждена. Оповещения Prometheus проверены в интерфейсе; доставка уведомлений внешним получателям не подтверждена.

## 3. Организационные барьеры

| Мера | Назначение | Статус |
|---|---|---|
| Постановка задачи и критерии приемки | Согласовать ожидаемое поведение до реализации | Описание подготовлено; номер Issue не зафиксирован в материалах |
| Отдельная функциональная ветка | Изолировать изменение | Выполнено: feature/lab8-trip-return-filter |
| Pull Request | Обеспечить обсуждение и прослеживаемость изменений | Выполнено: PR #36 |
| Независимое Code Review и обязательные проверки перед merge | Не допустить единоличного обхода проверок | Рекомендуется; обязательность не подтверждена |
| Контролируемое согласование выпуска | Проверить готовность среды и сохранить исходное состояние | Рекомендуется; локальный выпуск и сравнение выполнены |
| Runbook | Установить порядок диагностики и восстановления | Подготовлен и сохранен в Git |
| Снимки BEFORE и AFTER | Сравнить фактическое состояние системы | Выполнено в локальном Docker Desktop |
| Postmortem | Зафиксировать причину, влияние, хронологию и корректирующие действия | Расследование выполнено, отчет подготовлен |
| Версионирование конфигурации и доказательств | Обеспечить аудит и воспроизводимость | Реализовано в Git; итоговые материалы оформляются в docs/lab8-release-evidence |
| Проверка и улучшение процесса после инцидента | Снизить задержку обнаружения и предотвратить регрессии | Повторный эксперимент выполнен, добавлены тесты правил |

## 4. Пример работы барьеров при выпуске

Функциональное изменение — необязательный фильтр `has_return_date` для `GET /api/v1/trips`. Значения `true` и `false` фильтруют записи по наличию даты возвращения. Без параметра сохраняется прежнее поведение; некорректное значение возвращает HTTP 400 согласно контракту FishTrack.

- 48 тестов прошли на SQLite и PostgreSQL, в том числе 5 новых тестов фильтрации.
- Покрытие кода составило 63,13% при пороге 40%; Bandit не выявил проблем в проверенной области.
- Пройдены семь контейнерных проверок, миграции и дополнительные проверки собранного образа.
- PR #36 объединен с `develop`; GitHub Actions FishTrack CI #116 имеет общий статус Success.
- Merge-коммит: `5d682aa68fd16bf4274c005e769d5ae81db228e2`.
- Локально собран и развернут образ `fishtrack:sha-5d682aa68fd16bf4274c005e769d5ae81db228e2`. Это локальная сборка того же коммита, а не подтвержденный экземпляр артефакта Registry.
- После локального обновления оба экземпляра готовы, PostgreSQL и мониторинг сохранены; Smoke Test и 60 контрольных запросов прошли.

Ограничение: отдельные результаты публикации и завершения CD на собственной копии app-server не подтверждены. Порт staging 8081 недоступен с Windows. Успешный общий статус workflow и локальная приемка не заменяют проверку этого окружения. Независимое подтверждение Monitoring CI после отправки изменений пункта 14 также необходимо сохранить, если оно еще не зафиксировано.

## 5. Пример работы барьеров при инциденте

В локальной среде смоделирована остановка PostgreSQL. Журналы базы подтвердили остановку, структурированные журналы приложения — ответы `/health` с HTTP 503 на обоих экземплярах. Метрики оставались доступны (`up = 1`), но готовность снизилась до нуля (`fishtrack_app_healthy = 0`). Правило FishTrackNotReady перешло в Pending, затем в Firing уже после начала восстановления. PostgreSQL запущена обратно, оба экземпляра восстановили готовность, оповещения снялись, Smoke Test прошел. Исходный неполный автоматический отчет дополнен историческими журналами и отдельной проверкой восстановления.

После расследования добавлено правило FishTrackBothInstancesNotReady: оно обнаруживает одновременную потерю готовности двух экземпляров при доступности их метрик. Интервал вычисления 5 секунд, выдержка `for: 5s`; прежние правила сохранены. Добавлены регрессионные сценарии и Monitoring CI. Само правило указывает на общий симптом, а не доказывает отказ PostgreSQL без дополнительной диагностики.

| Измерение в повторном эксперименте | Результат |
|---|---:|
| Новое правило, Firing | 30,129 с |
| Старое правило, первый экземпляр | 55,211 с |
| Старое правило, оба экземпляра | 65,260 с |
| Выигрыш относительно первого срабатывания | 25,082 с (45,43%) |
| Выигрыш относительно обоих экземпляров | 35,131 с (53,83%) |

Результаты относятся к одному контролируемому локальному отказу; точность ограничена интервалом опроса около 5 секунд. Это экспериментальное подтверждение улучшения, а не гарантированный SLA обнаружения для всех инцидентов.

## 6. Взаимодействие барьеров

1. Задача и критерии приемки определяют требуемое поведение.
2. Отдельная ветка и локальные проверки снижают вероятность внесения дефекта.
3. Pull Request и CI обеспечивают проверку изменений до выпуска. Обязательное одобрение и запрет обхода проверок рекомендуются как отдельные меры защиты ветки.
4. Проверенный образ связывается с коммитом через SHA-тег; CD выполняет предусмотренную приемку.
5. Журналы, метрики и правила обнаруживают и объясняют эксплуатационные проблемы.
6. Runbook и Smoke Test помогают восстановить систему и проверить результат.
7. Postmortem переводит выявленную проблему в корректирующее действие и регрессионную проверку.

В FishTrack реализован многоуровневый подход к качеству выпуска и эксплуатации. Автоматические проверки снижают риск дефектов, наблюдаемость обеспечивает обнаружение и диагностику, а организационные меры определяют порядок принятия решений и восстановления. Повторный эксперимент показал, что аналогичный отказ обнаружен раньше. Для окончательного подтверждения сквозного выпуска на собственной виртуальной машине необходимо завершить проверку staging; наличие обязательной защиты ветки и внешней доставки уведомлений не следует считать подтвержденным без отдельной проверки.
